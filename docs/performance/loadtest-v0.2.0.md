# Нагрузочное тестирование v0.2.0

- Дата: 2026-10-30
- Версия: 0.2.0
- Инструмент: [`tools/perf/loadtest.py`](../../tools/perf/loadtest.py)
- Связано: [ADR-0002](../architecture/adr-0002-data-model-and-concurrency.md) (опрос изменений), [ADR-0001](../architecture/adr-0001-platform-and-stack.md) (целевая нагрузка)

## Цель

Проверить, что новая платформа выдерживает нагрузку компании на 1000–2000 сотрудников (требование, общее
с todo-planner), и найти узкие места до перехода на production.

## Стенд

- Docker Compose из репозитория: PostgreSQL 16, backend (gunicorn), frontend (nginx), backup.
- База — перенос production-снимка 1.0.1 от 30.10.2026 (17 сотрудников, 12 проектов, 19 планов, 463 строки,
  4098 записей реестра); самый большой план — 147 строк.
- 4 vCPU Intel Xeon 2,1 ГГц, 15 ГБ ОЗУ; генератор нагрузки работает на той же машине и отнимает часть
  процессора — на выделенном сервере запас больше.
- Запросы идут через nginx (порт 39663), как у сотрудников. Каждый поток — отдельное keep-alive соединение.

## Сценарии

| Сценарий | Что делает | Почему важен |
| --- | --- | --- |
| Опрос изменений | `GET /api/plans/<id>/changes?since=<ревизия>` без изменений | Открытый план опрашивает сервер каждые 4 с (вкладка в фоне — раз в 30 с). Это основная фоновая нагрузка |
| Открытие плана | `GET /api/plans/<id>` — план на 147 строк | Открытие проекта и переключение вкладок |
| Список проектов | `GET /api/projects` со статистикой по каждому проекту | Главная страница |
| Правка строки | `POST /api/plans/<id>/ops` — одна правка; все потоки правят один план | Худший случай: все одновременно правят один план (правки одного плана выполняются по очереди под блокировкой строки плана) |

## Найдено и исправлено

1. **Ответы 502 при перезапуске процессов gunicorn.** У рабочих процессов gthread перезапуск по
   `max_requests` (защита от утечек памяти) обрывал уже принятые, но ещё не начатые соединения: nginx отвечал
   502. Под этой нагрузкой процесс перезапускается раз в несколько десятков секунд, в обычной работе — раз в
   несколько минут; сотрудник видел бы редкую ошибку сохранения (клиент повторяет отправку сам) или
   пропущенный опрос. Backend переведён на процессы sync, как в todo-planner; число процессов по умолчанию —
   2 × ядра + 1 (не больше 9). Проверка: `GUNICORN_MAX_REQUESTS=300` — 19 перезапусков процессов за прогон,
   ни одной ошибки. Пропускная способность выросла на 30 %, p95 снизился в 2–3 раза.
2. **Запись в базу на каждый тихий опрос.** Отметка «сейчас на плане» обновлялась при каждом опросе — то есть
   запись в PostgreSQL раз в 4 секунды от каждого открытого плана. Теперь отметка обновляется не чаще раза
   в 15 секунд (срок жизни отметки — 45 секунд) или когда сотрудник начинает или заканчивает правку; тихий
   опрос — только чтение. Тест `test_quiet_poll_does_not_rewrite_presence`.

## Оценка для 1000–2000 сотрудников

Пусть в пиковый час систему открыла четверть из 2000 сотрудников (500), из них у 300 план на экране, у 200 —
во вкладке в фоне:

- опрос: 300 / 4 с + 200 / 30 с ≈ **82 запроса/с**;
- открытия планов, переходы, правки — с запасом ещё **20–30 запросов/с**.

Итого около 110 запросов/с — примерно пятая часть измеренной пропускной способности тихого опроса
(≈ 500 запросов/с) на 4 vCPU, которые делит с генератором нагрузки. Задержка открытия плана при этом
остаётся в пределах десятков миллисекунд.

Правки одного плана выполняются строго по очереди (блокировка строки плана — гарантия, что одновременные
правки не теряются, см. ADR-0002): ≈ 80 правок в секунду на один план. Даже 40 человек, непрерывно правящих
один и тот же план, получают ответ за 0,5–0,6 с; на практике план одновременно правят единицы. Правки разных
планов друг друга не ждут.

## Как повторить

```bash
# стенд: docker compose с перенесённой базой (docs/manuals/deployment-guide.md); пароль тестового администратора
python3 tools/perf/loadtest.py http://127.0.0.1:39663 --login admin --password '…' --seconds 15 --threads 10,40
```

Сценарий правок создаёт проект «Нагрузочный тест» на 150 задач и в конце убирает его в корзину. Запускайте
только на тестовом стенде.

## Ограничения

- Генератор и стенд на одной машине; сеть — локальная.
- Один сеанс на все потоки (вход ограничен по частоте); проверки доступа для разных сотрудников стоят столько
  же, сколько для одного.
- Ограничение попыток входа хранится в памяти процесса (`RATELIMIT_STORAGE_URI=memory://`): у каждого
  процесса backend свой счётчик, фактический предел — до N × `LOGIN_RATE_LIMIT` на учётную запись. Для
  строгого общего предела нужно общее хранилище (Redis).
