# ADR-0013. Полномочия без роли администратора

- Статус: принято
- Дата: 2026-11-05
- Версия: 0.7.2
- Связано: ADR-0004 (роли и доступы), ADR-0008 (структура компании), ADR-0014 (состояние системы); «По Делу» ADR-0044
  (полномочия capabilities)

## Контекст

Администрирование «Пульса» было доступно только роли «Администратор»: кадровику, чтобы вести структуру, службе
поддержки, чтобы заводить учётные записи, и дежурному инженеру, чтобы смотреть состояние сервиса, приходилось
выдавать всё — все проекты, доступы, ключи и настройки. В «По Делу» та же задача решена точечными полномочиями
(capabilities): администратор выдаёт сотруднику отдельные участки, роль при этом не меняется.

## Решение

### Список полномочий

`users.capabilities` — JSON-список ключей (миграция `0008_user_capabilities`, по умолчанию `[]`). Реестр —
`backend/app/capabilities.py` и тот же список в `src/utils/capabilities.js` (модульный тест сверяет ключи и подписи).

| Ключ | Подпись | Открывает |
| --- | --- | --- |
| `system.health` | Смотрит состояние системы | `GET /api/system/health`, `POST /api/system/health/check` (ADR-0014) |
| `modules.manage` | Настраивает модули | `/api/settings/jira*`, `/api/settings/podelu` (подключение), `/api/settings/podelu/links` (без выпуска ключа) |
| `calendar.manage` | Ведёт производственный календарь | `PUT`/`DELETE /api/calendar/<день>` |
| `audit.view` | Смотрит реестр изменений | `/api/audit`, фасеты, выгрузка CSV |
| `users.manage` | Ведёт учётные записи | `/api/users` (создание, изменение, удаление, фото), `/api/users/export`, `/api/users/import*` |
| `org.manage` | Ведёт структуру компании | `/api/departments*`, `/api/org/settings`, `/api/org/export`, `/api/org/import/*`; в `PATCH /api/users/<id>` — только подразделение, должность, руководитель |
| `access.manage` | Выдаёт доступы к проектам | `/api/access*`; направления — создание, изменение (как у менеджера), порядок и удаление |
| `trash.manage` | Управляет корзиной | удаление проекта, корзина всех проектов, восстановление и удаление навсегда |

### Проверки

- `security.has_capability(user, *keys)` — хотя бы одно; `capability_required(*keys)` — декоратор маршрута;
  `require_capabilities(user, *keys)` — все сразу. У администратора — все полномочия, у отключённого — никаких.
- Только администратору: роль «Администратор», выдача полномочий (`capabilities` в `PATCH /api/users/<id>`),
  ключи доступа (`/api/settings/integration-keys`, ключ «Пульса» для «По Делу»), вход через домен
  (`/api/settings/ldap`). Ключ открывает другой системе проекты, а настройки домена — вход сотрудников: это доступ
  ко всему, а не участок администрирования.
- **Защита учётных записей.** `can_manage_account(actor, target)`: «Ведёт учётные записи» не меняет учётные
  записи администраторов и сотрудников, у которых есть полномочия, которых нет у него самого, — иначе, сменив
  пароль такой учётной записи, он получил бы её права. Свои роль, вход, логин и включение сотрудник с полномочием
  не меняет. Импорт сотрудников, загруженный не администратором, пропускает такие учётные записи и роль
  «Администратор» из файла (предупреждение в плане).
- Синхронизация с AD (`POST /api/org/sync/ad`) и загрузка из «По Делу» (`POST /api/org/sync/podelu`) меняют
  и структуру, и учётные записи — не администратору нужны оба полномочия, `org.manage` и `users.manage`.
- Выдача и снятие полномочий — запись реестра «Сотрудники», поле «Полномочия» (подписи через запятую).

### Клиент

- `/api/auth/me` и списки сотрудников отдают `capabilities`; `auth.can(...keys)` в хранилище, ключ `'admin'` —
  только администратору.
- Маршруты администрирования помечены `meta.capability`; `/admin` открывает первый доступный раздел. Боковое меню
  показывает только доступные разделы; руководство администратора читает любой сотрудник с полномочиями.
- Карточка сотрудника: полномочия по группам («Система», «Люди и доступы», «Проекты») — только у администратора;
  у защищённых учётных записей — пояснение и только поля структуры. Профиль показывает свои полномочия.

## Последствия

- Роли не меняются: полномочие добавляет раздел администрирования, но не доступ к проектам (кроме
  `trash.manage` — удаления проекта и корзины).
- Новое полномочие — ключ в двух реестрах, проверка на маршрутах, раздел в `ADMIN_SECTIONS` и строка в
  руководстве администратора.

## Рассмотренные варианты

- **Отдельные роли** («Кадровик», «Поддержка») — роль у сотрудника одна, а участки сочетаются; ролей
  понадобилось бы по числу сочетаний.
- **Полноценные роли с правами в таблице** — сложнее в настройке и проверке; восьми фиксированных полномочий
  хватает, список расширяется.
