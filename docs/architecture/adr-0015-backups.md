# ADR-0015. Резервные копии: расписание в «Пульсе», копии — служба backup

- Статус: принято
- Дата: 2026-11-06
- Версия: 0.7.3
- Связано: ADR-0013 (полномочия), ADR-0014 (состояние системы); руководство по развёртыванию, «Резервное
  копирование и восстановление»

## Контекст

До 0.7.3 контейнер `backup` делал копию раз в сутки в `BACKUP_HOUR` и хранил ежедневные копии
`BACKUP_RETENTION_DAYS` дней — обе настройки в `.env` на сервере. Администратор «Пульса» не мог ни поменять
расписание, ни сделать копию перед рискованной операцией, ни увидеть, работает ли служба: остановленный контейнер
замечали, только когда копия была нужна. Копии вручную и перед обновлением не удалялись никогда.

## Решение

### Связь через базу

Приложение не получает ни файлов копий, ни доступа к Docker: служба и «Пульс» обмениваются через `app_settings`.

| Ключ | Кто пишет | Что |
| --- | --- | --- |
| `backup_settings` | «Пульс» | `enabled`, `time` «ЧЧ:ММ», `days` (1–7, 1 — понедельник), `retentionDays` (1–365), `keepManualDays` (0 — всегда) |
| `backup_request` | «Пульс» | «Сделать копию сейчас»: `requestedAt`, `by`; служба снимает запрос и делает копию `manual` |
| `backup_status` | служба | итог последней копии (`ok`, `at`, `lastOkAt`, `file`, `size`, `label`, `error`), `lastDailyDate`, `running`, список копий (`files`, до 60), `count`, `totalBytes`, действующее расписание (`service`, с часовым поясом службы и `source`: `settings` или `env`) и `seenAt` |

`backup_status` пишется слиянием JSON (`||`), поэтому время последней удачной копии переживает неудачную.

### Служба (`deploy/backup.sh loop`)

Раз в минуту — шаг `tick`: прочитать настройки (нет записи — `BACKUP_HOUR`/`BACKUP_RETENTION_DAYS`, как в 0.7.2;
база недоступна — прежние), выполнить запрос копии, сделать копию по расписанию, если сегодня день копий, время
наступило и сегодняшней ещё не было (`lastDailyDate`; так служба догоняет копию, пропущенную, пока она стояла),
раз в 5 минут — отметиться. Неудачная копия по расписанию тоже отмечает день: служба не повторяет её каждую
минуту, а «Состояние системы» показывает неполадку. Хранение — после каждой копии: `daily` старше
`retentionDays`, остальные (`manual`, `pre-update`, `pre-restore`) старше `keepManualDays`, если он не 0.
Скрипт — для busybox в `postgres:16-alpine` (`find … -exec rm`, а не `-delete`; проверен под busybox 1.36).

### Приложение

- `GET /api/system/backups` — администратору, «Смотрит состояние системы», «Ведёт резервное копирование»;
  `PUT /api/system/backups/settings` и `POST /api/system/backups/run` — администратору и новому полномочию
  `backups.manage` «Ведёт резервное копирование». Запрос при уже запрошенной или идущей копии — 409. Изменения —
  в реестре («Настройки», «Резервные копии»).
- Время следующей копии считается по расписанию службы и её смещению от UTC (`service.utcOffset`) и
  показывается в её часовом поясе.
- «Состояние системы»: служба не отмечалась 15 минут — неполадка; копии по расписанию выключены — замечание;
  ждать копию можно наибольший промежуток между днями расписания (у ежедневного — сутки, по будням — трое суток)
  плюс 2 часа (дальше — замечание) или 26 часов (дальше — неполадка).
- Раздел «Администрирование → Резервные копии»: состояние службы, последняя и следующая копия, расписание и
  хранение, «Сделать копию сейчас», список копий, команды восстановления.

## Последствия

- Обновление с 0.7.2 ничего не меняет, пока администратор не сохранит расписание: служба работает по `.env`.
- Восстановление по-прежнему — на сервере (`backup.sh restore`): база останавливается, а это не действие из
  браузера.
- Копии остаются на том же сервере; перенос на другой сервер — `rsync` инженера сопровождения (руководство по
  развёртыванию).

## Рассмотренные варианты

- **Копии из backend по расписанию** — понадобились бы `pg_dump` и каталог копий в образе backend и блокировка,
  чтобы копию делал один процесс из нескольких; служба `backup` уже есть и работает отдельно.
- **Управление через Docker API** — доступ к сокету Docker из приложения равен доступу ко всему серверу.
