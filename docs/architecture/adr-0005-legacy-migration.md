# ADR-0005. Перенос данных 1.0.x без потерь

- Статус: принято
- Дата: 2026-10-30
- Версия: 0.2.0
- Связано: ADR-0002 (модель данных), [runbook перехода](../runbooks/v0.2.0-migration-from-1.0.1.md)

## Контекст

Система в production; данные должны сохраниться полностью: сотрудники с паролями и фото, направления,
проекты, все вкладки-версии планов, строки со всеми полями, связи, комментарии, история строк, пометки,
исполнители, настройки графиков, доступы и весь реестр изменений. Формат 1.0.x — один JSON на проект со
вложенными строками JSON (`__tabs.tabsData`); база SQLite в режиме WAL (часть последних изменений — в файле
`puls.db-wal`).

## Решение

### Перенос

`backend/scripts/import_legacy.py <puls.db> [--report отчёт.md] [--dry-run]`:

1. Копирует `puls.db` вместе с `-wal` и `-shm` во временный каталог и открывает копию: исходные файлы не
   меняются (проверено контрольными суммами). Проверяет `PRAGMA integrity_check`.
2. Переносит в **пустую** базу 0.2 в одной транзакции: идентификаторы сотрудников, направлений и проектов
   сохраняются (ссылки и закладки остаются верными), счётчики последовательностей PostgreSQL выставляются
   после переноса.
3. Вкладки проекта → планы в прежнем порядке; ключи строк, пометок и исполнителей — прежние. Комментарии с
   ответами → `item_comments`; история строк → журнал плана (`plan_events`, пометка «из 1.0»); фото →
   `user_avatars`; группы проектов → направления; правила доступа → `access_rules` (дубли объединяются с
   наибольшим уровнем); реестр → `audit_log`. Для каждого плана сохраняется снимок «Перенос из 1.0».
4. **Сверка.** Каждый перенесённый план выгружается обратно в формат 1.0.x (`legacy_format.plan_to_legacy_state`)
   и сравнивается с исходной вкладкой поле за полем: строки, даты, статусы, прогресс, сдвиги, связи и лаги,
   исполнители, категории, цвета, текст на полосах, ссылки, комментарии и ответы, история строк, пометки,
   настройки графика. Любое расхождение — ошибка, транзакция откатывается, база 0.2 остаётся пустой.
5. Отчёт Markdown: что перенесено (количество), результат сверки, замечания (например, лишние пробелы в ФИО,
   объединённые дубли правил, вкладка без данных).

`--dry-run` выполняет перенос и сверку и откатывает транзакцию — репетиция без записи. Повторный запуск в
непустую базу запрещён (`--replace` — только для репетиций).

### Проверка самой проверки

- Тесты на реальном снимке production-базы от 30.10.2026 (`legacy/snapshot/puls-2026-10-30.db`, сессии
  удалены): перенос и сверка на SQLite и PostgreSQL.
- Тесты-мутации: в перенесённые данные вносится по одному искажению (дата, статус, связь, комментарий, пометка,
  настройка…) — сверка обязана его найти.
- CI переносит снимок в PostgreSQL на каждом коммите и прикладывает отчёт к результатам; задание Docker
  повторяет перенос через профиль `migrate` в собранных образах.

### Результат на снимке 30.10.2026

17 сотрудников (16 фото), 3 направления, 12 проектов, 19 планов, 405 задач, 31 веха, 27 групп, 5 пометок,
32 исполнителя, 18 комментариев, 1269 записей истории строк, 89 правил доступа (3 дубля объединены),
4098 записей реестра; 6 значений ФИО, email и должностей очищены от лишних пробелов. Сверка — без
расхождений.

## Последствия

- Переход — разовая процедура: остановить 1.0.1, перенести последнюю базу (с WAL) с сервера, проверить отчёт,
  запустить 0.2. Прежняя установка не меняется и служит откатом.
- Сессии 1.0.1 не переносятся (ADR-0003). Закрытые в 1.0.1 вкладки, данные которых 1.0.1 уже удалила, не
  восстанавливаются — их нет в базе.
- Экспорт плана в JSON формата 1.0 остаётся: план можно открыть и в старой версии.
