# ADR-0012. Импорт из MS Project и возможности MS Project в «Пульсе»

- Статус: принято; в 0.7.0 реализованы разделы 2–4, 5.1, 5.4, 5.5, 5.9; в 0.7.1 — недостающие пункты этих разделов и уточнения по проверке на настоящих файлах
- Дата: 2026-11-02
- Версия: 0.7.0 и далее (план работ — в конце)
- Связано: ADR-0002 (данные и операции плана), ADR-0005 (перенос 1.0.1), ADR-0006 (диаграмма Ганта),
  ADR-0007 (Jira), ADR-0008 (структура компании), ADR-0010 (задачи «По Делу»), ADR-0011 (ключи интеграций)

## Контекст

Многие руководители проектов ведут графики в MS Project: там заказчик принимает план, там посчитан критический
путь, там базовый план для отчёта. Перенести такой график в «Пульс» сейчас можно только вручную — строку за
строкой. Нужно:

1. Загружать файл MS Project в «Пульс» без ручного набора — новым проектом, новым планом или обновлением плана,
   который ведётся в MS Project.
2. Взять из MS Project то, что действительно помогает «Пульсу», и не превращать «Пульс» в MS Project: «Пульс» —
   общий для команды и руководства график с совместной правкой, статусами, Jira и структурой компании, а не
   система расчёта ресурсов и стоимости.

Что важно в нынешней модели «Пульса» (ADR-0002, ADR-0006):

| Свойство «Пульса» | Следствие для MS Project |
| --- | --- |
| У задачи одна связь «предшественник» (`dependency_key`, тип FS/SS/FF/SF, лаг в днях); веха не может быть последующей | В MS Project у задачи сколько угодно предшественников, у вех — тоже; это главный разрыв |
| Даты — дни, без часов; длительность в календарных или рабочих днях по производственному календарю РФ | В MS Project — минуты, рабочее время по календарю проекта, ресурса и задачи |
| Один исполнитель на строку (`assignee_key`), исполнители плана связаны с сотрудниками | В MS Project — несколько назначений с единицами и трудозатратами |
| Группы (сроки по вложенным), задачи могут иметь вложенные задачи | Суммарные задачи MS Project ложатся на группы |
| «Сдвиг» (`offset`) — отставание от планового окончания, хвост на полосе | Отклонение от базового плана MS Project ложится на сдвиг |
| Пометки строк (`plan_notes`) — флажок с датой и текстом | Крайний срок MS Project ложится на пометку |
| Версии плана — полные снимки (`plan_snapshots`) | Базовый план — частный случай снимка |
| Одна правка — не больше 2000 операций (`MAX_OPS`) | Импорт крупного файла — серверной операцией, как перенос 1.0.1 и копия плана |

## Решение

### 1. Форматы

| Формат | Откуда | Решение |
| --- | --- | --- |
| **MS Project XML** (MSPDI, `.xml`) | MS Project 2007–2021 и 365: «Файл → Сохранить как → XML (*.xml)» | **Основной путь** с 0.7.0. Открытая документированная схема (`mspdi_pj15.xsd`), разбирается стандартной библиотекой Python, без внешних программ |
| **`.mpp`** (двоичный) | Обычный файл MS Project | С 0.7.x через **необязательный конвертер**: отдельный контейнер с библиотекой MPXJ (Java, LGPL) переводит `.mpp` в MSPDI, дальше — тот же путь. Без контейнера «Пульс» предлагает сохранить файл как XML |
| `.mpx`, Primavera P6 (XER, XML), ProjectLibre `.pod`, GanttProject `.gan` | Старые версии MS Project, другие планировщики | Тем же конвертером — MPXJ читает их все; отдельной работы не требует |
| Project Online, Project для веба | Облако Microsoft (Dataverse, Graph) | Не делаем: нужна интеграция с учётной записью Microsoft; вернуться, если появится спрос |
| Excel-выгрузка MS Project | «Экспорт → Excel» | Не делаем: в таблице теряются иерархия, связи и календарь — XML даёт всё это без потерь |

Почему конвертер — отдельный контейнер, а не библиотека в backend: MPXJ — Java; JVM в образе backend
удвоила бы его размер и время запуска у всех, кому `.mpp` не нужен. Контейнер `mpp-converter` включается
профилем Compose (`docker compose --profile mpp up -d`), backend обращается к нему по внутренней сети
(`MPP_CONVERTER_URL`), файл передаётся и возвращается в памяти, наружу контейнер не открыт. Для закрытого
контура образ собирается заранее вместе с остальными (раздел «Установка в закрытом контуре»).

### 2. Конвейер импорта

```
файл ─► чтение ─► модель MS Project ─► сопоставление с «Пульсом» ─► план загрузки ─► применение
        (MSPDI;     (задачи, связи,      (параметры загрузки,          (предпросмотр:     (одна транзакция,
        .mpp — через  календари,          правила раздела 3)            что будет создано, снимок до и после,
        конвертер)    ресурсы, базовые                                 предупреждения)    событие истории)
                      планы)
```

- **Чтение** — потоковый разбор XML (`iterparse`) с защитой от сущностей и внешних ссылок (`defusedxml`, чистый
  Python), ограничения: файл до 50 МБ при разборе (загрузка через веб — до 25 МБ, `MAX_CONTENT_LENGTH` и nginx), до 20 000 задач, до 200 000 назначений. Файл не сохраняется — только
  разбирается.
- **Модель MS Project** (`services/msproject/model.py`) — неизменяемые записи: проект, календари, задачи
  (UID, GUID, уровень, WBS, даты, длительность, % выполнения, факт, ограничение, крайний срок, базовые планы,
  заметки, гиперссылка, настраиваемые поля), связи (предшественник, тип, лаг с единицей), ресурсы, назначения.
  Одна модель для MSPDI и для всего, что даёт конвертер.
- **Сопоставление** (`services/msproject/mapping.py`) — чистые функции «модель + параметры → документ плана
  «Пульса» + предупреждения», без базы: проверяются тестами на файлах-образцах.
- **План загрузки** — как в «Импорте и экспорте» структуры: сначала **Проверить** (числа групп, задач, вех,
  связей, исполнителей; дерево первых уровней; предупреждения сгруппированы — «связи суммарных задач: 4»,
  «ограничения кроме «Как можно раньше»: 12»), затем **Применить**. Повторная проверка после смены параметров
  не требует повторной загрузки файла (файл держит браузер, как снимок «По Делу» в 0.4.0).
- **Применение** — сервером, одной транзакцией, без ограничения 2000 операций: так же, как перенос 1.0.1 и копия
  плана. В истории плана — событие «Импорт из MS Project: <файл>», до изменения существующего плана — снимок
  «До импорта», после — снимок «Импорт из MS Project» (из него же — базовый план, раздел 5.3).
- **Куда**: «Новый проект → Из MS Project», «+ План → Из MS Project» в строке вкладок, «Заменить содержимое
  плана» (с подтверждением; снимок «До импорта» позволяет вернуть) и **«Обновить из MS Project»** (раздел 4).
- **API**: `POST /api/import/msproject/preview` (файл или ранее разобранный документ + параметры → план
  загрузки, отпечаток), `POST /api/import/msproject/apply` (то же + отпечаток → проект или план). Права — как на
  создание проекта (администратор, менеджер) или правку плана (обновление).

### 3. Сопоставление MS Project → «Пульс»

| MS Project | «Пульс» | Решение и предупреждения |
| --- | --- | --- |
| Проект: Название, Заголовок | Проект: название; план: название | Задача UID 0 (суммарная задача проекта) — не строка |
| Суммарная задача | Группа | Сроки группы считаются по вложенным, как в MS Project |
| Задача | Задача | Начало и окончание — даты из файла (окончание в 08:00 — предыдущий день). Длительность: по умолчанию «по дате» — график совпадает с MS Project день в день. Параметр «Длительности в рабочих днях» переводит задачи в режим «по длительности» с рабочими днями; если по производственному календарю «Пульса» даты разойдутся с файлом, план загрузки покажет, у скольких задач |
| Веха (Milestone = 1 или длительность 0) | Веха | Дата — начало |
| Неактивная задача, пустая строка | — | Пропускаются, число — в предупреждениях |
| Повторяющаяся задача | Группа с вхождениями | Как в MS Project |
| Связь FS/SS/FF/SF | Связь того же типа | Лаг переводится в дни: рабочие («5д») — в рабочие дни, прошедшие («5ед») — в календарные, в часах — с округлением, в процентах — от длительности предшественника. До 0.7.0 (одна связь) берётся ведущая — та, что определяет начало, остальные перечислены в предупреждениях; с 0.7.0 переносятся все (раздел 5.1) |
| Связь суммарной задачи | Связь первой/последней вложенной задачи | В «Пульсе» группы не связываются: связь переносится на вложенные и помечается в предупреждениях |
| Связь с задачей другого проекта | — | Пропускается с предупреждением |
| % выполнения, Факт. окончание | Прогресс, статус, дата завершения | 0 % — «Новая», 100 % — «Завершена» с датой факт. окончания, иначе — «В работе» |
| Базовый план 0 | Плановые сроки и сдвиг (параметр «Сроки по базовому плану») или базовый план «Пульса» (раздел 5.3) | По умолчанию — текущие сроки задачи и базовый план «Пульса» из базового плана 0: отклонение видно сразу |
| Крайний срок | Крайний срок строки (раздел 5.4); до него — пометка «Крайний срок» на строке | |
| Ограничение «Начало не ранее» | Ограничение строки (раздел 5.4) | Остальные ограничения (фиксированное начало и окончание, «не позднее») переносятся как сведения: показываются в карточке, на расчёт не влияют |
| Ресурс-работник | Исполнитель плана | Связывается с сотрудником по email, затем по ФИО (ё = е, без учёта регистра); остальные — исполнители без связи. Материальные и затратные ресурсы — не переносятся |
| Назначения | Исполнитель строки | Несколько назначений — исполнитель с наибольшими трудозатратами, остальные — в заметке строки; до раздела 5.7 |
| Заметки задачи | Первый комментарий строки «Заметка из MS Project» | Без форматирования (RTF не переносится) |
| Гиперссылка | Ссылка Jira, если адрес — задача подключённой Jira; иначе — в заметке | |
| WBS, номер структуры | Номер строки (раздел 5.5) | |
| Настраиваемое поле (Текст1…, Флаг1…, с псевдонимом) | Категория строки — по выбору в параметрах загрузки | Значения поля становятся категориями плана с цветами палитры |
| Приоритет, затраты, трудозатраты, типы задач, разбиение задач, календари задач и ресурсов | — | Не переносятся; число затронутых задач — в предупреждениях |
| Календарь проекта: рабочая неделя и исключения | Календарь плана (раздел 5.6); до него — сведения в плане загрузки | |
| UID и GUID задачи, GUID проекта | `extra.msp` строки, `settings.source` плана | Нужны для обновления из файла (раздел 4) и экспорта обратно |

### 4. Обновление плана из MS Project

Частый сценарий: график ведёт руководитель проекта в MS Project, а «Пульс» — место, где его видят команда и
руководство, где идут статусы, комментарии и Jira. Тогда план «Пульса» помечается как **ведущийся в MS Project**
(`settings.source = {kind: "msproject", projectGuid, fileName, importedAt}`), а **Обновить из MS Project**:

- сопоставляет строки по GUID задачи (затем по UID — для файлов без GUID), показывает план изменений: новые,
  изменённые (поле «было → стало»), отсутствующие в файле;
- обновляет только то, что пришло из файла: название, иерархию, сроки, связи, прогресс, исполнителя; не трогает
  то, что живёт только в «Пульсе»: комментарии, пометки, ссылки Jira, цвета, категории, если они заданы в «Пульсе»;
- строки, которых нет в файле, по умолчанию не удаляет — предлагает отдельной отметкой;
- применяется одной правкой, которую можно отменить, со снимком «До обновления из MS Project».

В карточке строки такого плана поля, которые перезапишет следующее обновление, помечены «ведётся в MS Project».
Обратное направление — **экспорт в MS Project XML** (раздел 5.9): план «Пульса» открывается в MS Project, если
руководитель решит вести его там.

### 5. Возможности MS Project для «Пульса»

Оценка: ценность для команды и руководства «Пульса»; трудоёмкость S — дни, M — до двух недель, L — больше.

| Возможность MS Project | Ценность для «Пульса» | Труд | Решение |
| --- | --- | --- | --- |
| Несколько предшественников, связи вех | Высокая: без этого не перенести ни один реальный график | L | **0.7.0** (5.1) |
| Критический путь, общий и свободный резерв | Высокая: где срыв двигает конец проекта | M | **0.8.0** (5.2) |
| Базовые планы и отклонения | Высокая: отчёт заказчику «план — факт» | M | **0.8.0** (5.3) |
| Крайние сроки и ограничение «не ранее» | Высокая при малой цене | S | **0.7.0** (5.4) |
| Номер структуры (WBS) | Средняя: «пункт 2.3 плана» в переписке с заказчиком | S | **0.7.0** (5.5) |
| Календарь плана (рабочая неделя, исключения) | Средняя: шестидневки, праздники заказчика | M | **0.8.0** (5.6) |
| Загрузка исполнителей | Высокая для руководства направления | L | **0.9.0** (5.7) |
| Временная шкала (Timeline) для руководства | Высокая для отчётов и презентаций | M | **0.9.0** (5.8) |
| Экспорт в MS Project XML | Средняя: обратный путь к заказчику | M | **0.7.0** (5.9) |
| Сводный график (вставленные проекты) | Средняя: направление на одном графике | L | Позже (5.10) |
| Трудозатраты, единицы, типы задач (фикс. объём работ и т. п.) | Низкая для команды «Пульса», высокая сложность | L | Не делаем; оценка в часах — только как сведения (5.7) |
| Выравнивание загрузки ресурсов | Низкая: результат автоматического выравнивания редко принимают | L | Не делаем |
| Стоимость, бюджет, освоенный объём (EVM) | Низкая для текущих пользователей | L | Не делаем |
| Разбиение задач, повторяющиеся задачи | Низкая | M | Не делаем (импорт — раскрытием, раздел 3) |
| Планирование от даты окончания, ALAP | Низкая | M | Не делаем |
| Календари задач и ресурсов | Низкая; отпуска сотрудников — забота «По Делу» | L | Не делаем; отпуска — через интеграцию с «По Делу», если появятся там |

#### 5.1. Связи: таблица вместо поля строки

- Новая сущность плана **связь** — таблица `plan_links` (`plan_id`, `key`, `from_key`, `to_key`, `type`
  FS/SS/FF/SF, `lag` в днях, `lag_kind` — рабочие или календарные дни, служебные поля как у пометок и
  исполнителей). Операции `link.create`, `link.update`, `link.delete`, `link.restore` — в той же очереди, с той же
  ревизией, отменой и историей, что строки и пометки (ADR-0002). Связь удалённой строки удаляется вместе с ней
  и возвращается при восстановлении.
- Миграция переносит `dependency_*` каждой строки в связь и удаляет столбцы на следующем выпуске (сначала —
  чтение из обоих мест, как при переносе 1.0.1: данные не теряются ни при обновлении, ни при откате).
- Последующей может быть и веха: её дата — окончание (FS) или начало (SS) предшественника с лагом.
- Автосдвиг: для последующей задачи ограничение — наибольшее из всех предшественников (FS/SS — на начало,
  FF/SF — на окончание), как в MS Project; длительность сохраняется. Цикл связей запрещён при создании связи
  (проверка графа на сервере и в клиенте), а не только пропускается при расчёте.
- Интерфейс: в карточке строки — список «Предшественники» и «Последующие» с типом и лагом; на диаграмме —
  перетаскивание от края полосы к полосе создаёт связь, как в MS Project; стрелки рисуются для всех связей.
- Затронутое: расчёт автосдвига (`domain/dependencies.js`), очередь правок, копия плана, перенос 1.0.1,
  экспорт CSV, перенос из Jira (свободная дата задачи со связями — раздел «Автоперенос» ADR-0007), фильтр
  «Со связями». Тесты паритета с 1.0.1 сохраняются: у перенесённых планов по одной связи на задачу.

#### 5.2. Критический путь и резерв

- Чистая функция `computeSchedule(items, links, calendar)` — прямой и обратный проход: ранние и поздние
  начало и окончание, общий и свободный резерв в рабочих днях, признак «критическая». Считается в клиенте при
  каждой правке (как автосдвиг) и в сервере для статистики; 5000 строк — миллисекунды.
- Конец проекта — самое позднее окончание; крайние сроки (5.4) учитываются как ограничения окончания.
- «Вид → Критический путь»: критические задачи — красной обводкой, резерв — тонким хвостом после полосы;
  фильтр «Критические»; колонка «Резерв, дн»; в статистике — «Критических задач», «Резерв до конца проекта».
- Для перенесённых из MS Project планов расчёт совпадает с MS Project при одинаковом календаре — это
  проверяется тестом на файле-образце (критические задачи из файла против рассчитанных).

#### 5.3. Базовые планы

- Базовый план — именованный снимок плана (`plan_snapshots`, `reason = "baseline"`), до трёх на план;
  `settings.baselines = [{id, name, snapshotId, savedAt}]`, один выбран для сравнения.
- «Сохранить базовый план» — в меню версий; при импорте из MS Project базовый план 0 становится базовым планом
  «Пульса».
- На диаграмме — тонкая серая полоса базовых сроков под полосой строки (включается в «Виде»); в подсказке и
  колонках — «Отклонение начала / окончания, дн»; в статистике — сколько задач ушли от базового плана и на
  сколько; в выгрузке PNG/PDF — обе полосы.
- Сдвиг (`offset`) остаётся: это отметка «знаем, что опоздаем» внутри текущего графика, а базовый план —
  автоматическое сравнение с утверждённым. Отчёт «план — факт» строится по базовому плану.

#### 5.4. Крайние сроки и ограничение «не ранее»

- Поля строки `deadline` (дата) и `constraint` (`{type: "snet", date}`; типы из MS Project, кроме «не ранее»,
  хранятся как сведения).
- Крайний срок — зелёная стрелка на строке; если окончание (со сдвигом) позже — стрелка красная, строка
  попадает в фильтр «Срыв крайнего срока» и в статистику. Автосдвиг не сдвигает задачу раньше даты «не
  ранее».
- Перенос из Jira: срок задачи Jira можно переносить в крайний срок, а не в окончание (параметр
  автопереноса) — для команд, где Jira хранит обязательства, а «Пульс» — план.

#### Решения при реализации 5.1 и 5.4 (0.7.0)

- Связь — `{key, from, to, type, lag, lagKind}` (`lagKind`: `calendar` по умолчанию или `working`), операции
  `link.create | update | delete | restore`; правка может менять и концы связи. Повтор связи между теми же строками и
  цикл отклоняются (400, цикл — код `link_cycle`), граф проверяется и в сервере, и в клиенте до отправки.
- Событие истории связи пишется на последующую строку (`entity = "link"`, `entityKey` — её ключ, ключ связи — в
  `changes.link`): связь видна в истории строки, сроки которой она задаёт.
- Связь удалённой строки удаляется вместе с ней; при восстановлении строки возвращаются её связи, удалённые не раньше
  строки, если они не дают повтора или цикла. Невозможный уже `link.restore` (например, при отмене) не отклоняет
  пакет: связь остаётся удалённой и попадает в `fixes`.
- Поля `dependencyKey/Type/Lag` в операциях строк переводятся в связи — для документов и скриптов до 0.7.0 и
  страницы, открытой до обновления; правка единственного предшественника у строки с несколькими предшественниками
  отклоняется. Документ плана и снимки — версия 2 со списком `links`; снимки и файлы версии 1 читаются
  (предшественник строки становится связью), восстановление снимка сверяет связи по паре строк.
- Миграция `0007_plan_links` переносит предшественников живых и удалённых строк (связь удалённой строки — удалённая),
  столбцы `dependency_*` остаются до следующего выпуска; откат записывает в них первую связь задачи.
- JSON формата 1.0: первый предшественник — в поля 1.0, все связи строки — в дополнительное поле `predecessors`,
  крайний срок и ограничение — в поля `deadline`, `constraintType`, `constraintDate`; 1.0.x их не читает, импорт
  «Пульса» — читает. Сверка переноса 1.0.1 не сравнивает тип и лаг связи у задачи без предшественника.
- Ограничение — два поля строки, `constraintType` и `constraintDate` (вместо объекта `constraint`), крайний срок —
  `deadline`; у задач и вех. «Начало не ранее» держит начало задачи (и дату вехи) и без связей — при автосдвиге и
  «Выровнять по связям»; остальные ограничения MS Project показываются в карточке как сведения.
- Автосдвиг: связи FS/SS дают начало, FF/SF — окончание, при тех и других — самое раннее начало, при котором выполнены
  все; закреплённая дата переноса из Jira (keepFreeDates) сохраняется, если все связи задачи одного рода. Лаг в
  рабочих днях — по календарю плана, FS с таким лагом начинается со следующего рабочего дня.
- API интеграций: у строк добавлены `predecessors` и `deadline` (полей предшественника там раньше не было).
  CSV: столбцы «№», «Крайний срок» и «Предшественники» (`3FS+2д;5SS`: «д» — календарные, «рд» — рабочие дни).
- По итогам ревью: цикл проверяется один раз на пакет, по итоговому графу (алгоритм Кана); только при найденном
  цикле связи пакета внутри него перепроверяются по одной — так сообщение называет связь, а цепочка из 20 000 строк,
  записанная снизу вверх, загружается так же быстро, как сверху вниз. Связь строки с её родительской или вложенной
  строкой запрещена (как в MS Project). Восстановление версии — серверный пакет без ограничения 2 000 операций и без
  возврата связей сверх тех, что есть в версии; идентификаторы MS Project (`extra.msp`) пишут только серверные пакеты
  (импорт, копия плана, восстановление версии). В клиенте большая правка с автосдвигом уходит частями по 1 500
  операций с одной отменой; смена статуса двигает последующие, только если меняется окончание, от которого они
  считаются; задача с длительностью в рабочих днях сохраняет число рабочих дней при сдвиге по связи.

#### 5.5. Номер структуры

- Колонка «№» — номер по дереву (1, 1.2, 1.2.3), пересчитывается при перестановке; при импорте из MS Project —
  код WBS из файла, если он не совпадает с номером (настраиваемые коды WBS).
- Номер — в поиске («2.3»), подсказке, выгрузке CSV и печати.

#### 5.6. Календарь плана

- `settings.calendar = {workWeek: [1, 2, 3, 4, 5], exceptions: [{date, working, title}]}` поверх
  производственного календаря РФ: шестидневка, праздники заказчика, рабочие выходные проекта.
- Рабочие дни задач, лаги в рабочих днях, резерв и критический путь считаются по календарю плана.
- Импорт: рабочая неделя и исключения базового календаря проекта MS Project.

#### 5.7. Загрузка исполнителей

- Исполнители планов связаны с сотрудниками (0.3.0), поэтому загрузку можно посчитать **по всем проектам**: в
  неделю — сколько задач у сотрудника идут одновременно и, если задана оценка в часах (поле строки «Оценка, ч»;
  из Jira — трудозатраты), сколько часов при его рабочей неделе.
- Экран «Загрузка» для менеджеров и руководителей направлений: сотрудники подразделения или направления по
  неделям, перегрузка подсвечена, щелчок — задачи с переходом в план. Доступ — только к проектам, которые
  сотрудник и так видит (ADR-0004).
- Без единиц назначения и выравнивания: «Пульс» показывает перегрузку, решает её руководитель.

#### 5.8. Временная шкала для руководства

- Отметка строки «На временную шкалу» (вехи и ключевые задачи); над диаграммой — одна полоса с отмеченным, как
  Timeline в MS Project.
- «Экспорт → Временная шкала (PNG, SVG)» — картинка для презентации заказчику; несколько шкал — по планам
  проекта на одной картинке.

#### 5.9. Экспорт в MS Project XML

- План → MSPDI: группы — суммарные задачи, задачи и вехи, все связи с лагами, исполнители — ресурсы с
  назначениями, выбранный базовый план — базовый план 0, крайние сроки и ограничения, комментарии — заметки,
  календарь плана — календарь проекта. GUID строк, пришедших из MS Project, сохраняются — файл ложится на
  исходный проект без дублей.
- Проверка: экспорт → импорт даёт тот же план (тест кругового обхода).

### 6. Безопасность и данные

- Разбор XML — без внешних сущностей и с ограничением размера; `.mpp` — только через изолированный конвертер
  без доступа к сети и базе.
- Файл не хранится; в плане сохраняются только сопоставление строк (`extra.msp`) и источник
  (`settings.source`). ФИО и email ресурсов попадают только в исполнителей плана — как при ручном вводе.
- Импорт в новый проект доступен тем, кто создаёт проекты; обновление — тем, кто правит план; всё — в реестре
  изменений.

## Последствия

- Графики из MS Project переносятся в «Пульс» без ручного набора, а обновление из файла позволяет вести график в
  MS Project и показывать его команде в «Пульсе» — со статусами, Jira и комментариями.
- Модель связей меняется (5.1): это самая крупная правка с 0.2.0 — она затрагивает расчёт сроков, очередь
  правок, перенос 1.0.1 и Jira, поэтому идёт первой и с полным набором тестов паритета.
- «Пульс» сознательно не берёт из MS Project трудозатраты, стоимость и выравнивание: команда видит график,
  руководство — отклонения и загрузку, а расчёт ресурсов остаётся у тех, кому он нужен, в MS Project.
- Конвертер `.mpp` — необязательный компонент с Java; без него всё работает через «Сохранить как XML».

## Решения при реализации (разделы 2–4 и 5.9)

Пакет `backend/app/services/msproject/` (чистый Python): `reader.py`, `model.py`, `mapping.py`, `schedule.py`,
`diff.py`, `writer.py`, `text.py`; тесты — `backend/tests/test_msproject.py` на файлах
`backend/tests/fixtures/msproject/` и `src/gantt/domain/__tests__/msprojectConsistency.test.js`.

- **Чтение без `defusedxml`** (новых зависимостей нет): пролог до корневого элемента разбирает сам expat с
  обработчиками объявлений — DOCTYPE, сущность или нотация дают отказ, и кодировку (UTF-16 без метки, объявление)
  он определяет так же, как основной разбор; внешние сущности expat не загружает. Ограничения: 50 МБ, 20 000 задач
  (без суммарной задачи проекта), 50 000 ресурсов, 200 000 назначений, 5000 календарей, вложенность 32. `.mpp`
  (OLE), ZIP, PDF и `.mpx` узнаются по первым байтам. Даты вне диапазона MS Project (1984–2149) — пустые
  (задача без дат пропускается с предупреждением), границы исключений календаря прижимаются к нему.
- **Текст** — без NUL, управляющих символов и одиночных суррогатов (RTF `\'00`, `\u0`, `\u55296`); `\uN` вне
  Юникода пропускается. Любая ошибка арифметики дат при сопоставлении — `MsProjectError`, а не ошибка сервера.
- **Начало рабочего дня** — самое раннее начало рабочего времени в неделе календаря проекта (иначе
  DefaultStartTime, иначе 08:00); окончание в это время и раньше — предыдущий день. Начало не сдвигается.
- **Лаги** — в дни так, как MS Project ставит задачи при днях целиком: FS и SS — вниз (+4ч после окончания в
  17:00 — следующее утро, лаг 0; −4ч — тот же день, −1), FF — вверх, SF — вверх и на день раньше (в «Пульсе» SF
  кончает задачу в день начала предшественника, в MS Project — к его началу; экспорт прибавляет этот день
  обратно). Прошедшие единицы — календарные дни, проценты (LinkLag хранит сами проценты, как читает MPXJ) — доля
  длительности предшественника в рабочих днях; больше 3650 дней — ограничивается.
- **Даты файла — главные** (`schedule.py`): после перевода лагов они подбираются так, чтобы расчёт «Пульса»
  (те же правила, что `computeDependencyShifts`, с производственным календарём плана) дал ровно даты файла: у
  каждой последующей строки определяющая связь равна её дате, остальные её не превышают; рабочий лаг, который не
  попадает в дату (дата — нерабочий день «Пульса»), становится календарным. «Начало не ранее» позже начала
  задачи прижимается к началу. Изменённые лаги — в предупреждении «Лаги связей подобраны…». При загрузке по
  базовому плану лаги не подбираются: сроки строк там плановые, и расчёт должен показать отставание. Совпадение
  проверяют обе стороны: pytest на файлах-образцах и случайном файле пишет документы в
  `src/gantt/domain/__tests__/fixtures/msproject-*.json`, vitest проверяет, что автосдвиг их не двигает.
- **Шкала плана** — не длиннее 15 лет (иначе план не создать): при более широком разбросе — по срокам проекта,
  затем 15 лет от его начала (предупреждение). Исключения календаря разворачиваются только в пределах шкалы ± год
  и не больше 50 000 дат; ограничение без даты не переносится (предупреждение).
- **Связь суммарной задачи** переносится по смыслу типа: со стороны предшественника — вложенная задача с самым
  поздним окончанием (FS, FF) или самым ранним началом (SS, SF), со стороны последующей — самое раннее начало
  (FS, SS) или самое позднее окончание (FF, SF); при равенстве — первая/последняя по порядку. Связь строки с
  самой собой пропускается, повторы объединяются, связь, замыкающая цикл, отбрасывается (последняя по файлу).
- **Группа** не получает сроков, крайнего срока, ограничения и исполнителя (предупреждения). Категория — только у
  задач; поле-флаг даёт категорию с названием поля, если флаг установлен; цвета — по порядку появления значений.
- **Исполнители** — все ресурсы-работники с ФИО, в том числе без назначений; сотрудник связывается только при
  единственном совпадении. Из назначений строки — наибольшие трудозатраты, затем единицы, затем порядок файла.
  Заметка строки одна: текст заметки, ссылка не на Jira, «Также назначены: ФИО (N ч)».
- **Документ загрузки** сверх формата плана содержит `calendar` (рабочая неделя и исключения — для 5.6),
  `baseline` (базовый план 0 по строкам — для 5.3), `customFields` (выбор поля категорий) и `options`.
- **Обновление**: сначала все совпадения по GUID, затем по UID (если у одной из сторон GUID нет).
  «Заблокирована» сохраняется, пока файл не скажет «Завершена»; исполнитель — поле MS Project, только если в
  файле есть ресурсы; сдвиг — только при загрузке «по базовому плану»; категория и ссылка Jira заполняются, только
  если в «Пульсе» пусто. Порядок: позиции строк, уже стоящих в нужном порядке, сохраняются (наибольшая
  возрастающая подпоследовательность), остальные встают между соседями. Строка, сменившая тип, создаётся заново
  (`item.delete` + `item.create`). «Отсутствующие в файле» — только строки с `extra.msp`, чьей задачи в файле
  нет; строки «Пульса» и копии строк из файла не удаляются никогда. Связи меняются только между строками из
  файла. `item.update` может нести `extra` (новый UID/GUID/WBS). `reserved_keys` — все ключи плана, включая
  корзину: новые строки, связи и исполнители их не получают. Строка, удалённая в «Пульсе» и оставшаяся в файле,
  возвращается новой строкой со свежим ключом (`deletedInPuls`, предупреждение `deleted_in_puls`), а не
  восстановлением: тип и родитель могли смениться, комментарии остаются в корзине.
- **Экспорт**: задачи по умолчанию с ручным планированием — MS Project открывает график день в день, не пересчитывая;
  `scheduling="auto"` закрепляет даты ограничением «Начало не ранее». Задача с подзадачами — суммарная (её
  собственные даты не выгружаются). Сдвиг — базовый план 0 (плановые сроки) и окончание со сдвигом. Категория —
  «Текст1» с псевдонимом «Категория», ссылка Jira — гиперссылка, комментарии — заметки. Элементы пишутся строго в
  порядке схемы `mspdi_pj15.xsd`; недопустимые в XML символы удаляются; повторный GUID заменяется новым. UID
  берутся из `extra.msp` (до 2³¹ − 1) и из ключей исполнителей `a<до 7 цифр>`; остальным — по порядку.

## Уточнения 0.7.1 (перепроверка после 0.6.1)

Найдены перепроверкой: перенос базы 0.6.1 со снимка 1.0.1, наборы тестов 0.6.1 на коде 0.7.0, 181 настоящий
файл MSPDI (MS Project 2002–2019, `.mpp`, сконвертированные MPXJ, файлы других программ, планы на 8 и 20 тысяч
задач). Отчёт — `docs/review/v0.7.1-recheck-after-0.6.1.md`.

- **Автосдвиг** (5.1): строка, чьё начало (окончание) связи не сдвигают, не меняется вовсе; сдвинутая задача «в
  рабочих днях» сохраняет число рабочих дней своих сроков — по датам, а не по полю `duration` (у перенесённых из
  1.0.1 строк оно бывает устаревшим). Связь подзадачи с родительской задачей, разрешённая до 0.7.0, правится,
  копируется и восстанавливается; запрет — только для новой связи и смены её концов.
- **Срок задачи Jira** (5.4): настройка плана `jiraDue` — `end` (окончание, по умолчанию) или `deadline` (крайний
  срок строки; сроки плана не меняются).
- **Номер** (5.5): ищется при включённой колонке «Номер»; в CSV — столбец «Номер» (по структуре, у мастер-копии —
  WBS из файла), в PNG/PDF/SVG — перед названием при включённой колонке.
- **Версии** (2): после любой загрузки — версия «Импорт из MS Project» (`reason = "after_import"`).
- **Окончание в начале дня** — конец предыдущего *рабочего* дня недели календаря проекта (понедельник 08:00 —
  пятница), а не календарного.
- **«Сроки по базовому плану»**: лаги подбираются по текущим срокам файла (MS Project рассчитал их по этим
  связям), строки получают плановые сроки и сдвиг. Без отставания расчёт ничего не двигает; несогласованы только
  строки, которые и в MS Project начинаются позже плана. Подбор по плановым срокам отвергнут: у выгруженных из
  «Пульса» планов начало последующей уже учитывает сдвиг предшественника, и отставание считалось бы дважды.
- **Обновление**: исполнитель сопоставляется по сотруднику, затем по ресурсу (ключ `a<UID>`; переименованный ресурс
  переименовывает исполнителя), затем по ФИО. Предупреждения плана обновления — в общем списке окна: файл без GUID,
  у большинства совпавших по UID строк другие названия (`uid_names_differ`); строки «Пульса» после строк файла, чьи
  сроки меняются (`puls_rows_follow`, их выравнивает «Выровнять по связям»).
- **Экспорт**: email сотрудников — только в выгрузке администратора. Веха — на 17:00: SS от неё — лаг на день
  меньше, SF — без поправки на день (иначе MS Project ставит последующие на день позже; проверено пересчётом
  выгрузки планировщиком MPXJ по правилам MS Project).
