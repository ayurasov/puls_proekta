# v0.2.0: переход с 1.0.1 на новую платформу

Эксплуатационная инструкция к [ADR-0005](../architecture/adr-0005-legacy-migration.md). Переход разовый:
1.0.1 останавливается, её база переносится в PostgreSQL 0.2 со сверкой каждого плана, 0.2 запускается на том же
порту 39663. Прежняя установка (`/puls_proekta`, служба `puls`) **не меняется** и остаётся вариантом отката.

Простой для сотрудников — 5–10 минут (раздел 3). Подготовку и репетицию (разделы 1–2) можно сделать заранее
в рабочее время: они не влияют на работающую 1.0.1.

## 0. Что нужно

- Сервер Ubuntu 22.04/24.04 с работающей 1.0.1 (каталог `/puls_proekta`, служба systemd `puls`, порт 39663).
- Права `sudo`, 2 ГБ свободной памяти, 5 ГБ на диске.
- Доступ сервера к репозиторию `puls_proekta` и к реестру образов Docker (Docker Hub или зеркало компании).
- 15 минут, когда в системе никто не работает (или предупреждение сотрудникам).

Перенос берёт **рабочую базу с сервера** (`/puls_proekta/puls.db` и `puls.db-wal`), а не из git: в git лежит
снимок на момент коммита.

## 1. Подготовка (без простоя)

### 1.1. Docker

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
docker compose version
```

### 1.2. Новая установка рядом со старой

```bash
sudo git clone --branch v0.5.0 <адрес репозитория puls_proekta> /opt/puls
cd /opt/puls
sudo cp .env.example .env
sudo chmod 600 .env
openssl rand -hex 32   # → SECRET_KEY
openssl rand -hex 24   # → POSTGRES_PASSWORD
sudo nano .env
```

В `.env` заполните `SECRET_KEY` и `POSTGRES_PASSWORD`. Порт оставьте `HTTP_PORT=39663`. Если сотрудники
открывают систему через nginx на самом сервере (порт 80 или 443 проксирует на `127.0.0.1:39663`, см.
`/etc/nginx/sites-enabled/puls`), укажите `HTTP_BIND=127.0.0.1` — тогда порт 39663 не виден снаружи, а
nginx сервера продолжит работать без изменений. `BOOTSTRAP_ADMIN_PASSWORD` оставьте пустым: администраторы
переносятся из 1.0.1.

Если на машине уже работают другие системы на Docker (например, «По Делу»), задайте «Пульсу» диапазон адресов,
которого нет в сети компании, — файл `docker-compose.override.yml` (раздел «Рядом с другими системами на одной
машине» руководства по развёртыванию). Иначе Docker может выбрать диапазон, совпадающий с сетью компании, и на
машине перестанут работать доменные имена.

### 1.3. Сборка образов и база

```bash
cd /opt/puls
sudo docker compose build
sudo docker compose up -d db
sudo docker compose ps          # db — healthy
docker network inspect puls_default -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}'   # диапазон сети «Пульса»
```

Проверьте, что доменные имена и другие системы на машине по-прежнему работают. Backend до переноса не
запускайте: перенос выполняется в пустую базу.

### 1.4. Репетиция переноса на копии рабочей базы

Копия снимается «на ходу» средствами SQLite (согласованная, вместе с содержимым WAL), 1.0.1 продолжает работать:

```bash
sudo python3 - <<'EOF'
import sqlite3
src = sqlite3.connect("file:/puls_proekta/puls.db?mode=ro", uri=True)
dst = sqlite3.connect("/opt/puls/import/puls.db")
src.backup(dst)
dst.close(); src.close()
EOF

cd /opt/puls
sudo docker compose --profile migrate run --rm legacy-import \
  python scripts/import_legacy.py /import/puls.db --dry-run --report /import/rehearsal-report.md
```

`--dry-run` переносит, сверяет и **откатывает**: база 0.2 остаётся пустой. Откройте
`/opt/puls/import/rehearsal-report.md`:

- раздел «Перенесено» — количества сотрудников, проектов, планов, строк, комментариев, правил, записей реестра;
- раздел «Сверка» — «Каждый план выгружен обратно в формат 1.0.x и совпал с исходной вкладкой»;
- раздел «Замечания» — например, объединённые дубли правил доступа, очищенные пробелы в ФИО, вкладки без данных.

Если сверка нашла расхождение, команда завершается с кодом 2 и перечисляет расхождения — переход
откладывается, отчёт передаётся разработчику. Репетицию можно повторять сколько угодно.

После репетиции удалите копию: `sudo rm -f /opt/puls/import/puls.db*`.

## 2. Проверка перед переходом

- [ ] Репетиция прошла, расхождений нет, количества совпадают с ожидаемыми.
- [ ] `sudo docker compose ps` — `db` в состоянии healthy.
- [ ] В `.env` заданы `SECRET_KEY` (≥ 32 символов) и `POSTGRES_PASSWORD`; `HTTP_PORT=39663`.
- [ ] Сотрудники предупреждены о перерыве и о том, что после перехода нужно войти заново (пароли прежние).

## 3. Переход (простой 5–10 минут)

### 3.1. Остановить 1.0.1 и сохранить её базу

```bash
sudo systemctl stop puls
sudo systemctl disable puls          # не стартует после перезагрузки и не займёт порт 39663
sudo systemctl status puls --no-pager   # inactive (dead)

sudo mkdir -p /root/puls-1.0.1-final
sudo cp -a /puls_proekta/puls.db* /root/puls-1.0.1-final/
sudo ls -la /root/puls-1.0.1-final/
```

Файлы в `/root/puls-1.0.1-final/` — неизменяемый архив последнего состояния 1.0.1. Сам каталог
`/puls_proekta` не трогайте: это вариант отката.

### 3.2. Перенос

```bash
cd /opt/puls
sudo rm -f import/puls.db*
sudo cp -a /puls_proekta/puls.db* import/
sudo docker compose --profile migrate run --rm legacy-import
```

Команда применяет миграции, переносит базу со сверкой и пишет отчёт в `/opt/puls/import/import-report.md`
(тот же отчёт выводится на экран). Код завершения 0 — перенос записан; 2 — найдены расхождения, ничего не
записано (раздел 5).

### 3.3. Запуск

```bash
sudo docker compose up -d
sudo docker compose ps                                   # backend, frontend — healthy; db — healthy; backup — up
curl -fsS http://127.0.0.1:39663/api/health/ready; echo  # {"status":"ok","schema":"0005_podelu_links","version":"0.5.0"}
sudo docker compose exec backup sh /usr/local/bin/backup.sh now after-migration
```

## 4. Проверка после перехода

- [ ] Вход администратора по прежнему паролю; вход сотрудника через домен (если LDAP включён).
- [ ] «Проекты»: все направления и проекты на месте, прогресс и ближайшие вехи заполнены.
- [ ] Самый большой проект: все вкладки-планы, строки, связи, пометки, комментарии; «История плана → Журнал
      изменений» содержит записи «из 1.0»; «Версии» — снимок «Перенос из 1.0.1».
- [ ] «Администрирование → Сотрудники»: фото, роли, отключённые сотрудники.
- [ ] «Доступы → Кто что видит»: доступы как в 1.0.1 (наблюдатели — только просмотр, ADR-0004).
- [ ] «Реестр изменений»: последние записи 1.0.1 на месте.
- [ ] Старая ссылка вида `http://<сервер>:39663/#/project/5` открывает проект.
- [ ] Резервная копия `after-migration` создана: `sudo docker compose exec backup sh /usr/local/bin/backup.sh list`.

После проверки удалите рабочую копию из каталога импорта (архив остаётся в `/root/puls-1.0.1-final/`):

```bash
sudo rm -f /opt/puls/import/puls.db*
```

## 5. Если перенос нашёл расхождения

Ничего не записано, 1.0.1 остановлена — верните её и разберитесь спокойно:

```bash
sudo systemctl enable --now puls
```

Сохраните `/opt/puls/import/import-report.md` и передайте разработчику.

## 6. Откат после запуска 0.2

Пока не начали работать в 0.2 (в тот же день):

```bash
cd /opt/puls
sudo docker compose down          # без -v: база 0.2 сохраняется в томе
sudo systemctl enable --now puls  # 1.0.1 с последней базой, которую не меняли
```

Правки, сделанные в 0.2 после перехода, в 1.0.1 не попадут. Отдельный план можно перенести обратно вручную:
в 0.2 «Экспорт → JSON (открывается и в 1.0)», в 1.0.1 — импорт JSON во вкладку.

## 7. После перехода

- Через 2–4 недели стабильной работы: удалить службу `puls` (`sudo rm /etc/systemd/system/puls.service`,
  `sudo systemctl daemon-reload`), архивировать `/puls_proekta` и `/root/puls-1.0.1-final` по правилам
  хранения компании.
- Ветка `v1.0.1` содержит секрет сессий и рабочую базу 1.0.1 — после остановки 1.0.1 они не действуют, но
  доступ к репозиторию стоит ограничить (ревизия, Б1).
- Дальнейшие обновления — `sudo sh deploy/update.sh <версия>` (руководство по развёртыванию).
