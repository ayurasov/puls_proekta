# Release notes — v0.7.3

Ветка `v0.7.3` от `v0.7.2`. Регулярные резервные копии настраиваются в «Пульсе». Миграций нет. Обновление —
`sudo sh deploy/update.sh v0.7.3` из каталога установки.

## Зачем

Копии делал контейнер `backup` раз в сутки, а час и срок хранения задавались только в `.env` на сервере. Нельзя
было сделать копию перед рискованной операцией, увидеть, работает ли служба, и настроить копии не каждый день;
копии вручную и перед обновлением не удалялись никогда.

## Что нового

**Администрирование → Резервные копии** (ADR-0015):

- **Служба резервного копирования работает / не отвечает / ещё не подключалась** — отметка службы раз в 5 минут и
  что проверить на сервере, если её нет.
- **Последняя копия**, **Следующая по расписанию** (по часовому поясу службы), **Хранится** (число и общий размер).
- **Расписание и хранение**: копии по расписанию вкл/выкл, время, дни недели, сколько дней хранить копии по
  расписанию и остальные (вручную и перед обновлением; 0 — всегда). Служба применяет изменения в течение минуты;
  пока расписание не сохранено — действует расписание из `.env`.
- **Сделать копию сейчас** — служба делает копию в течение минуты; видно, кто её запросил, по готовности —
  уведомление.
- **Копии** — последние 60: когда, как сделана, размер; **Как восстановить базу из копии** — команды для сервера.
- Полномочие **«Ведёт резервное копирование»** — расписание и копии без роли администратора; «Смотрит состояние
  системы» видит раздел без права менять.

**Состояние системы**: карточка «Резервные копии» учитывает расписание (по будням выходные — не пропуск),
показывает следующую копию и считает неполадкой службу, которая не отмечалась 15 минут.

**Служба копий** (`deploy/backup.sh`): раз в минуту сверяет расписание и запросы из «Пульса»; если была остановлена
во время копии по расписанию — делает её после запуска в тот же день; неудачную копию по расписанию не повторяет
каждую минуту, а сообщает о ней.

## Совместимость

- Пока расписание в «Пульсе» не сохранено, служба работает по `BACKUP_HOUR` и `BACKUP_RETENTION_DAYS`, копии
  вручную и перед обновлением хранятся всегда — как в 0.7.2.
- После обновления служба один раз сделает копию за сегодня, если новая служба её ещё не отмечала.
- Восстановление — по-прежнему на сервере (`backup.sh restore`).

## Проверка

Сервер — 446 тестов, клиент — 293 модульных теста, e2e — 93 сценария. `deploy/backup.sh` проверен под busybox
1.36 (как в `postgres:16-alpine`) на PostgreSQL 16: расписание из `.env` и из «Пульса», догоняющая копия, копия по
запросу, день не из расписания, выключенное расписание, хранение копий по расписанию и остальных, неудача
`pg_dump` без повторов в тот же день, недоступная база; «Пульс» читает то, что записала служба, а служба — расписание,
сохранённое «Пульсом». По ходу найдено и исправлено: в некоторых сборках busybox нет `find -delete` — хранение копий
не работало бы, теперь `find -exec rm`.

- Сервер: расписание и хранение с проверкой и записью в реестр; кто видит и кто меняет; копия по запросу и 409 при
  запрошенной или идущей копии; сводка — служба, список копий, следующая копия по часовому поясу службы; карточка в
  «Состоянии системы» — служба не отвечает, расписание выключено, копия по будням в понедельник не опоздание, «не
  настроено».
- Клиент: размеры по-русски; полномочие в том же списке, что на сервере.
- e2e: расписание по будням и хранение, копия по запросу, повторный запрос — 409, ссылка из «Состояния системы»;
  «Смотрит состояние системы» — раздел только для просмотра.
