# Release notes — v0.7.1

Ветка `v0.7.1` от `v0.7.0`. Исправления по полной перепроверке всего, что изменилось после 0.6.1 (версия на
продакшене), и пункты ADR-0012 для 0.7.0, которых не хватало. Миграций нет. Обновление — `sudo sh
deploy/update.sh v0.7.1` из каталога установки (с 0.6.1 — сразу на 0.7.1, миграция `0007_plan_links` выполнится
при запуске).

## Зачем

Перед переходом продакшена с 0.6.1 на 0.7 всё, что изменилось, проверили заново тремя независимыми проверками:

- **обновление базы** — база 0.6.1 из снимка 1.0.1 с продакшена (19 планов, 463 строки, 157 связей) плюс правки
  через API 0.6.1, обновлённая на SQLite и PostgreSQL 16 и сравнённая построчно и через API;
- **поиск регрессий** — наборы тестов 0.6.1 (сервер, модульные, e2e) на коде 0.7.0 и два стенда рядом на одних
  данных;
- **настоящие файлы MS Project** — импорт, обновление мастер-копии и выгрузка на файлах, сохранённых MS Project.

Данные при обновлении не теряются (все таблицы совпадают построчно, каждая связь перенесена с тем же типом и
лагом). Главная найденная проблема — расчёт сроков 0.7.0 на перенесённых данных, она исправлена.

## Исправлено

### Автосдвиг на планах, перенесённых из 0.6.1

Задачи с длительностью «по длительности, в рабочих днях» в 0.7.0 при пересчёте брали длину из сохранённого поля
длительности, а у части строк, перенесённых из 1.0.1, оно не совпадает с датами (27 из 152 таких задач). Сразу
после обновления три плана показали бы «Сроки 43 / 21 / 2 строк не согласованы со связями» (в 0.6.1 — ни одной), а
правка одной задачи сдвигала цепочку до +7 дней вместо +1.

Теперь:

- строка, чьё начало (окончание) уже согласовано со связями, не меняется — как в 0.6.1;
- сдвинутая задача «в рабочих днях» сохраняет число рабочих дней своих сроков (по датам, а не по полю).

На перенесённом снимке число несогласованных строк в каждом плане совпадает с 0.6.1 (9 строк в двух планах, как и
было). **Отличие от 0.6.1, которое остаётся намеренно:** задача «в рабочих днях», сдвинутая связью, сохраняет
рабочие дни, а не календарный размах. Например, задача на 7 рабочих дней, сдвинутая на 31 декабря, кончается после
новогодних праздников, а не 6 января с шестью рабочими днями. Задачи с длительностью в календарных днях и «по
дате» сдвигаются как в 0.6.1.

### Связи, сделанные в 0.6.1

До 0.7.0 предшественником подзадачи можно было сделать её родительскую задачу; миграция такие связи переносит.
В 0.7.0 их нельзя было изменить, они пропадали при копировании плана и отмене удаления строки, а версия плана с
такой связью не восстанавливалась (ошибка 400). Теперь они правятся, копируются, возвращаются отменой и
восстанавливаются из версий 0.6.1 и 0.7; запрещено только создать новую такую связь.

Страница или скрипт, открытые до обновления, присылающие предшественника полем строки, снова не отклоняются
целиком из-за цикла или удалённого предшественника — связь снимается с отметкой, как в 0.6.1.

### Мелкие регрессии

- Поиск по числу («3») находил строки по номеру даже при скрытой колонке «Номер» — показывал весь третий раздел.
  Номер ищется только при включённой колонке.
- Под названием строки снова виден лаг связи: «лаг +2 д», при нескольких — «лаги +1 д, +2 рд».
- JSON (формат 1.0): изменения связей — снова в истории строки-последующей.

### MS Project на настоящих файлах

Импорт со стандартными параметрами на всех 181 файле прошёл без ошибок, даты совпали с файлом, расчёт «Пульса» не
нашёл ни одной несогласованной строки, выгрузка и повторная загрузка дают тот же план. Исправлено:

- **Выгрузка** — email сотрудников только в выгрузке администратора (раньше — у всех, кто видит план). Последующие
  задачи по связям SS и SF от вехи в MS Project больше не встают на день позже, чем в «Пульсе».
- **«Сроки по базовому плану»** — без отставания план больше не «не согласован»: лаги подбираются по текущим срокам
  файла, несогласованными остаются только строки, которые и в MS Project начинаются позже плана.
- **Обновление мастер-копии** — ресурс, переименованный в MS Project, остаётся тем же исполнителем с новым ФИО
  (раньше появлялся второй). Предупреждения: файл другого проекта без идентификаторов; строки «Пульса» после
  строк файла, сроки которых меняются (после обновления — «Выровнять по связям»). Предупреждения плана обновления
  теперь видны в окне загрузки.
- **Окончание в начале рабочего дня** (понедельник 08:00) — пятница, а не воскресенье.

## Чего не хватало по ADR-0012 для 0.7.0

- **Срок задачи Jira — в крайний срок** (5.4). В **Сверке и настройках Jira** — **Срок задачи Jira: В окончание /
  В крайний срок**. Второй вариант — для команд, где в Jira записаны обязательства: сроки плана не меняются, а
  срок из Jira становится крайним сроком строки (красная отметка, если окончание позже). Ручная сверка и
  автоперенос «Сроки» следуют настройке; в меню Jira — пометка. Настройка плана `jiraDue`: `end` (по умолчанию)
  или `deadline`.
- **Номер строки в выгрузках** (5.5). В CSV — столбец «Номер» по структуре плана (1.2.3; у мастер-копии — код WBS
  из файла); «№» — по-прежнему порядок выгрузки, на него ссылаются «Предшественники». В PNG, PDF и SVG номер
  стоит перед названием, если включена колонка «Номер».
- **Версия «Импорт из MS Project»** (раздел 2) — состояние плана сразу после любой загрузки из файла, рядом с
  «До импорта…» и «До обновления…» в **История → Версии**.

## Не входило в 0.7 (план ADR-0012)

Критический путь и резерв, базовые планы и отклонения, календарь плана — 0.8.0; загрузка исполнителей и
временная шкала — 0.9.0; чтение `.mpp` напрямую — отдельный выпуск 0.7.x с конвертером.

## Документация

- Руководство пользователя: `.mpp` (сохраните как XML), версии до и после импорта и как откатить замену или
  обновление, что обновление мастер-копии меняет и что сохраняет, поиск по номеру, «Срок задачи Jira», столбцы
  CSV.
- ADR-0012 — «Уточнения 0.7.1»; отчёт о перепроверке — [docs/review/v0.7.1-recheck-after-0.6.1.md](../review/v0.7.1-recheck-after-0.6.1.md).
- Руководство по развёртыванию: откат с 0.7.x на 0.6.x — восстановлением копии или откатом схемы и что при этом
  теряется.
