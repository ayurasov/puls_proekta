# Release notes — v0.3.1

Ветка `v0.3.1` от `v0.3.0`. Исправления после первого развёртывания 0.3.0 на рабочем сервере. **Миграций
нет**, сессии сохраняются. Обновление — `sudo sh deploy/update.sh v0.3.1` из каталога установки.

## Jira Server и Data Center

Что было: «Проверить подключение» отвечала «Соединение установлено», но задачи в планах помечались «нет в Jira
или нет доступа», поиск по ключу писал «Не найдены или недоступны», а запрос JQL — «Jira вернула ошибку 400:
Can not construct instance of java.lang.Boolean from String value 'warn'».

Причина: для пакетного чтения задач «Пульс» передавал `validateQuery: "warn"`. Строковые значения понимает
только Jira Cloud; Jira Server и Data Center ждут `true` или `false` и отклоняли каждый запрос. Тесты не
поймали ошибку: заглушка Jira в них принимала любое значение.

Что сделано:

- Задачи строк читаются одним запросом с `validateQuery: false`: несуществующий или недоступный ключ — не
  ошибка, такой задачи просто нет в ответе. Запрос JQL сотрудника Jira проверяет сама; ошибка показывается её
  словами: «Jira не приняла запрос: …».
- Если Jira всё же отклоняет запрос с одним ключом, задача читается напрямую (`/issue/KEY`) — ошибка больше не
  выглядит как «задачи нет».
- **Проверить подключение** — вход, вид и версия Jira и пробный поиск тем же запросом, что и в планах. Ответ:
  «Соединение установлено: svc-puls · Jira Server 8.20.10 · поиск задач работает». Если вход удался, а поиск
  нет, — «Вход выполнен, но поиск задач в Jira не работает: <причина от Jira>».
- «Нет в Jira» хранится в кэше минуту (найденные задачи — `JIRA_CACHE_SECONDS`, 5 минут): после исправления
  прав или создания задачи ждать не нужно. Отмеченные ошибочно задачи перечитаются при следующем открытии плана.
- Заглушки Jira в тестах сервера и в e2e теперь ведут себя как Jira Server: отклоняют строковый
  `validateQuery` и несуществующий ключ при проверке запроса.

## Развёртывание рядом с «По Делу»

- Перенос базы 1.0.x больше не зависит от `BOOTSTRAP_ADMIN_PASSWORD`. Раньше с заданным паролем перенос сначала
  создавал администратора и затем отказывался («В базе уже есть данные»), а с паролем короче 8 символов падал
  вместе с backend. Сообщение backend о коротком пароле подсказывает оба пути: новая установка — пароль
  длиннее, переход с 1.0.x — пустой пароль и перенос.
- Если после запуска «Пульса» на машине перестают работать доменные имена, а после `docker compose down` всё
  возвращается, — Docker выбрал для сети «Пульса» диапазон, совпадающий с сетью компании. В руководстве по
  развёртыванию — раздел «Рядом с другими системами на одной машине»: свой диапазон файлом
  `docker-compose.override.yml`, общий — `default-address-pools`, порты и число процессов на общей машине.
  Проверка диапазона добавлена в runbook перехода с 1.0.1.

## Главная и диаграмма

- Направление, в котором сотрудник не видит ни одного проекта, ему не показывается — ни на главной, ни в API.
  Администратор и менеджер (он выбирает направление для своих проектов) видят все направления.
- Подпись на полосе выбирается по воспринимаемому контрасту APCA вместо формулы WCAG 2, которая на насыщенных
  средних тонах выбирала чёрный текст: теперь на синих, красных, фиолетовых, серых и тёмных полосах (в том числе
  бледных — завершённых и заблокированных) подписи белые, на жёлтых, лаймовых, зелёных и голубых — чёрные.

## Проверка

  JQL, проверка подключения с поиском, один отклонённый ключ, перепроверка отсутствующей задачи), видимость
  направлений, сообщение о пароле первого администратора, окружение `legacy-import`.
- CI: перенос базы 1.0.1 в Docker с заданным `BOOTSTRAP_ADMIN_PASSWORD`; e2e Jira — на заглушке, отклоняющей
  строковый `validateQuery`.
